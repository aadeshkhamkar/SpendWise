# SpendWise Backend – Login and Signup Update

This backend is based on the supplied Java 21 / Spring Boot 3.5.7 project. Existing expense controller, service, entity and repository are retained. Authentication is added against the existing MySQL `expense_tracker.app_users` table.

## 1. Database expected

The code maps to the table already present in your database:

- `id` BIGINT primary key, auto increment
- `full_name` VARCHAR(120)
- `email` VARCHAR(190), unique
- `password_hash` VARCHAR(100)
- `role` VARCHAR(30)
- `created_at` TIMESTAMP, default current timestamp

No new table or SQL migration is required if your `DESCRIBE app_users;` output matches these columns.

## 2. Configure MySQL

Open `src/main/resources/application.properties` and set the actual local MySQL password:

```properties
spring.datasource.username=root
spring.datasource.password=YOUR_MYSQL_PASSWORD
```

Do not commit your real database password to GitHub. The current supplied project had `CHANGE_ME` as a placeholder.

## 3. Import into Eclipse

1. Extract this backend folder.
2. In Eclipse choose **File → Import → Maven → Existing Maven Projects**.
3. Select the extracted `backend` folder and finish.
4. Right-click the project → **Maven → Update Project**.
5. Ensure Eclipse uses JDK 21: **Project → Properties → Java Build Path** and **Java Compiler**.
6. Run `com.expense.tracker.ExpenseTrackerApplication` as a Java Application.

The `pom.xml` adds `spring-security-crypto` for BCrypt only. It does not add Spring Security's web filter chain, so the existing expense endpoints continue to behave as they did before.

## 4. Authentication endpoints

### Signup

`POST http://localhost:8080/api/auth/signup`

```json
{
  "fullName": "New User",
  "email": "newuser@example.com",
  "password": "at-least-8-chars"
}
```

Returns HTTP 201 with `{ "user": { "id": 1, "fullName": "New User", "email": "newuser@example.com", "role": "USER" }, "message": "Account created successfully." }`.

### Login

`POST http://localhost:8080/api/auth/login`

```json
{
  "email": "newuser@example.com",
  "password": "at-least-8-chars"
}
```

Returns HTTP 200 with the same `user` profile shape. Invalid credentials return HTTP 401. Duplicate signup email returns HTTP 409. Signup always assigns role `USER`; a public request cannot grant itself ADMIN.

The existing frontend reads `response.data.user`, so the response shape is compatible. This implementation deliberately does not return a fake bearer token.

- `GET /api/expenses/{id}`

- `DELETE /api/expenses/{id}`

## Important security scope

This update makes login and signup work and stores passwords as BCrypt hashes. It is not a complete production authentication system: there is no JWT/session issuance, no authenticated route enforcement, and the current expenses table has no user ownership column. Existing expense endpoints therefore remain publicly accessible as in the supplied backend and expense records are not isolated by account. Do not deploy this version publicly with real financial data until token/session security and per-user expense ownership are added.
